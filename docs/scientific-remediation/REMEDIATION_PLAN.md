# Scientific remediation plan for v0.1

**Status:** Phase 0 complete; Phase 1 foundations implemented and awaiting review by the domain
owner and an independent schema reviewer.
**Prepared:** 15 September 2026. **Prepared with AI assistance (Claude Opus 5); not a scientific sign-off.**
**Conclusion it carries:** all 650 v0.1 profiles are unsuitable for GA review until the shared
validation, comparison and generation foundations are fixed.

## 1. Where things stand

An independent scientific pre-review of all 650 profiles
([pre-review-2026-09-15/](pre-review-2026-09-15/)) found defects that the existing test suites
cannot catch, because those suites check that the code agrees with generated fixtures, and the
fixtures are generated by the same rules that are wrong.

Every one of those defects was turned into a reproducible test in
[`scientific-checks/v0.1/cases.json`](../../scientific-checks/v0.1/cases.json), run by both
implementations, and every one of them now passes. The file holds no open defect cases: all of them
have been promoted to guards, each carrying the commit that fixed it, so a regression re-breaks a
test rather than passing quietly. The table below is kept as the record of what was wrong.

| Symptom | Case | Decision |
|---|---|---|
| Raw counts vs log-normalised expression resolve as a direct match | BMCS-SCI-001 | D2 |
| Ensembl gene IDs vs HGNC symbols resolve as a direct match | BMCS-SCI-002 | D2, D7 |
| A value in mg and a value in s resolve as a direct match | BMCS-SCI-003 | D1, D2 |
| A firing rate converts nM to uM without loss | BMCS-SCI-004 | D1 |
| A firing rate declared in kg passes validation | BMCS-SCI-005 | D1 |
| g vs kg, Cel vs K, 1/s vs /min, uM vs mol/L are reported incompatible | BMCS-SCI-006..009 | D1 |
| An unspecified species meeting a human-only port is a contradiction | BMCS-SCI-010 | D5 |
| 110 conversion fixtures convert units of another quantity | BMCS-SCI-011 | D9 |
| 6 contradiction fixtures pair units of the same quantity | BMCS-SCI-012 | D9 |
| 17 positive fixtures put dimensional quantities on a probability scale | BMCS-SCI-013 | D8, D9 |
| Variants on GRCh37 and GRCh38 resolve as a direct match | BMCS-SCI-014 | D2, D7 |
| A simulated value satisfies a port that requires measured data | BMCS-SCI-015 | D2, D12 |

## 2. Corrections to the pre-review

These are errata against the 15 September report. The report stands as a fault report; these
points do not.

- **E1. The per-profile verdict split is withdrawn.** `136 BLOCK / 514 CHANGES_REQUIRED` implied a
  per-profile precision the evidence does not support, because nearly every defect originates in
  shared generator and comparison code. The per-profile table survives only as an index of which
  profiles show which symptom. The single conclusion is the one at the top of this document.
- **E2. S12 miscounted.** The 50 profiles that require `security.data_use` and
  `security.consent_scope` are 25 clinical and 25 epidemiology, not 50 clinical.
- **E3. The blanket item decisions are withdrawn.** The pre-review assigned one decision per item
  path across all 650 packets. Several were over-broad: `uncertainty.censoring` was marked
  *required* in 400 packets although its own reason limits it to time-to-event data;
  `semantic.ontology_terms` was marked *required* for all 650; `artifact.sha256` *required*
  wherever an artifact representation is allowed. Item levels are now decided per profile (D10),
  with the pre-review table as input only.
- **E4. Four conclusions were stated more absolutely than the science allows.**
  - Dense to sparse re-encoding is lossless **only** when the implicit entry's meaning (zero or
    unobserved), ordering, shape and dtype are declared equal (D6).
  - Celsius to kelvin is exact for **absolute** temperatures; a temperature difference converts
    with factor 1 and no offset and needs its own quantity kind (D1).
  - Identifier mapping is **not always** lossy: a pinned mapping that is total over the declared
    feature universe and bijective is lossless (D7).
  - "Any species" has no defined meaning yet, so the report should not have prescribed UNKNOWN. The
    test now asserts only that it is not a contradiction (D5).
- **E5. The sources are now pinned, with a caveat that matters.** `scripts/pin_sources.py` retrieved
  and hashed every citation into
  [sources/sources.lock.json](sources/sources.lock.json). Most entries are Crossref citation
  records, which pin the *reference* rather than the article: paywalled papers and licensed
  standards (ISO 80000-1, ISO 20776-1, SNOMED CT) cannot be retrieved here at all. Where a decision
  rests on the content of one of those, the reviewer must pin their own licensed copy and record the
  terms. The lock file labels every entry with which case it is.
- **E6. The change request was not in the repository.** It is now at
  [pre-review-2026-09-15/change-request.json](pre-review-2026-09-15/change-request.json) (8.6 MB)
  with the tools that produce it. Governance may prefer it as a release asset rather than a
  committed file; that is a maintainer decision.
- **E7. The change request answered questions the packets do not ask.** Corrected: it now carries
  5,829 answers, exactly the set the 650 packets ask.
- **E8. The published report now opens with these corrections.** The HTML page and the PDF were
  regenerated with a Corrections section, and the verdict split is labelled as withdrawn wherever
  it appears.
- **E9. S12 overstated the data-use ordering defect.** `security.data_use` is already a set-like
  path in `spec/v0.1/rules/normalization.json`, and normalised contracts compare as EXACT whatever
  the element order. The real defect is narrower and worth keeping: `compare_contracts` does not
  normalise internally, so a caller that skips the contract-normalisation stage gets INCOMPATIBLE
  from ordering alone, and `equal` on a set of DUO codes still carries no subsumption.

## 3. What this plan does not decide

It does not pick the final wording of any profile, and it does not approve anything. Each design
decision below carries its status: six are decided and implemented, and every one of them still
needs a named owner to accept it. A decision recorded here is an engineering choice with its
reasoning and sources attached, not an approval. No review evidence may be written to
`source/reviews/` until the profile it covers is both corrected and reviewed by qualified people.

## 4. Design decisions

Each decision needs an owner, a written record with pinned sources, and the tests it changes. All
are open, and each has a record to complete under [decisions/](decisions/).

### D1. Quantity kinds and units
**Question.** How are units validated, compared, and tied to the quantity a profile measures?
**Options.** (a) Keep the four-row table. (b) UCUM as the unit grammar plus dimensional analysis,
with a Biosimulant quantity-kind registry binding each profile's quantity to a dimension and a
canonical unit. (c) QUDT quantity kinds with UCUM codes.
**Recommendation.** (b). Checked against UCUM 2.2 (revision 2024-06-17): `[PFU]`, `[TCID_50]` and
`[hnsf'U]` exist; there is **no** `M` for molar, so `uM` in today's fixtures is not a UCUM code and
molar concentration is `umol/L`; `mol` is defined as a count, which is why mass concentration and
molar concentration are not interconvertible without a molar mass; `[BAU]` is a bioequivalent
*allergen* unit and must not be used for WHO binding antibody units.
**Sub-decisions.** Affine units (absolute vs difference quantity kinds); annotated units such as
`{person}`, `{cell}`, `{DW}`; mass-to-molar as a declared parameterised transformation; whether to
migrate fixture spellings (`uM` to `umol/L`) across 124 profiles.
**Tests.** BMCS-SCI-003..009, 011, 012; guards 102, 103, 105.

### D2. Comparing fields that both ports declare but the profile does not require
**Question.** Should a declared-on-both-sides field be compared?
**Options.** (a) Status quo: only required fields are compared. (b) Compare a defined list of
interpretation-changing items when both sides declare them (`missing: ignore`). (c) Compare
everything both sides declare.
**Recommendation.** (b). `spec/v0.1/catalogue/items.json` already promises this behaviour for all
266 items ("Checked only when the profile requires it or both contracts include it"), so either the
behaviour or the published wording must change.
**Tests.** BMCS-SCI-001, 002, 003.

### D3. Concept identity and external meaning
**Question.** What carries a port's scientific meaning?
**Recommendation.** Keep a Biosimulant-controlled term, minted outside the versioned profile IRI so
it is stable across profile versions, and require a mapping to external ontology terms **where an
external term exists and changes the compatibility answer** — decided per profile in the pilot, not
for all 650 at once (see E3).

### D4. Subject and biological-context vocabulary
**Question.** Should `semantic.subject`, tissue, cell type and compartment be controlled terms?
**Recommendation.** CURIEs from registered prefixes compared by subsumption against a pinned
snapshot; decide per profile whether the field gates compatibility at all. Core and simulation
profiles may need no subject.

### D5. Species and multi-organism context
**Question.** What does a species field mean, and what does "any" mean?
**Must define, distinctly.** Omitted (no evidence) → UNKNOWN; species-independent content;
a target that accepts any species; and multi-organism ports (host and pathogen, communities), which
one `NCBITaxon` value cannot express. Add taxonomic subsumption against a pinned NCBI Taxonomy
snapshot.
**Tests.** BMCS-SCI-010; guards 101, 106.

### D6. Representation equivalence
**Question.** When is a re-encoding lossless?
**Recommendation.** Only when implicit-entry meaning, ordering, shape and dtype are declared and
equal; otherwise UNKNOWN or a declared lossy transformation. Guard 104 must keep passing.

### D7. Identifier mapping and loss
**Recommendation.** Lossless only with a mapping snapshot pinned by digest that is total over the
declared feature universe and bijective; partial or one-to-many mappings are lossy and need
approval; no snapshot means UNKNOWN. **Test.** BMCS-SCI-002.

### D8. Scale, value domain and transform
**Recommendation.** Separate the measurement level (nominal, ordinal, interval, ratio) from the
value domain (proportion, probability, count) and the transform (log2, log10, ln, logit), and make
the log base explicit. **Test.** BMCS-SCI-013.

### D9. Fixture generation
**Recommendation.** Remove the name-substring heuristics; take units, scales and axes from
per-profile declarations; derive the conversion fixture from the profile's own dimension; make the
contradiction fixture cross-dimension; add target-side UNKNOWN fixtures.
**Tests.** BMCS-SCI-011, 012, 013.

### D10. Requirement levels for candidate items
**Recommendation.** Decide per profile or profile class, with a justification and source for each
item that gates compatibility. Default for everything else: declared but not gating. No item
becomes required across a domain without evidence that it changes the compatibility answer.

### D11. Transformation statuses
**Recommendation.** Every profile that permits lossy or inferred conversion gets fixtures for both
paths, and a declared transformation must carry its direction, parameters and digest. No profile
exercises these paths today.

### D12. Keeping the layers apart
**Question.** `compare_contracts` returns `policy_decision` next to the technical status, which
mixes two of the three layers `INTEGRATIONS.md` says to keep separate.
**Recommendation.** Keep the comparison result purely technical; map to policy in the
workspace-policy stage; keep Passport quality separate. Decide whether `policy_decision` stays in
the report schema for compatibility with existing consumers.

## 5. Sequence

The order follows the reviewer's: foundations, then a reviewed pilot, then regeneration, then
review by domain.

**Phase 0 — freeze and evidence. Complete**, except for the human acceptance below. Defect suite,
guards, this plan, the decision records, the pilot dossiers, and the scientific gate in `RELEASE.md`
step 5. *Exit:* suite runs in CI — done; plan accepted by the domain owner and an independent schema
reviewer — **outstanding, and not something this workstream can sign off on its own behalf.**

**Phase 1 — foundations. Implemented, pending review.** All twelve decisions now carry a recorded
decision. D1, D2, D8 and D9 are complete. D3, D4, D5, D6, D7, D11 and D12 are deliberately partial,
and each record states which half is implemented and which half is not. D10 is recorded but not
implemented: the one change that looked separable was built, measured at +29.7% of the bundle to
restate a list the review packets already publish, and withdrawn.

Two causes account for every deferral: work that needs pinned ontology or mapping snapshots, whose
ownership and licensing nobody has settled (D3, D4, D5, D7),
and work that needs a per-profile scientific judgement rather than a rule a generator can derive
(D6's allowed-kind narrowing, D7's mapping requirements, D10's profile classes, D11's per-profile
lossy and inference fixtures). Deriving those from profile names is the heuristic D9 abolished, so
they belong to the pilot and the domain waves, not to this phase.
55 of 58 sources are pinned by SHA-256; the three that are not are licensed (ISO ×2, SNOMED CT) and
are cited by identifier and version instead. *Exit:* `npm run test:scientific` green in both
languages — done; cross-language parity holds — done; regeneration is deterministic — done; each
decision has a written record with pinned sources — done for the decided six; guards still pass —
done. Review of this work by a qualified reviewer is **outstanding.**

**Phase 2 — reviewed pilot.** Specify the 20 pilot profiles from their dossiers, regenerate them,
and have qualified reviewers sign them off under `PROFILE_REVIEW.md`. *Exit:* 20 evidence files
under `source/reviews/`, each naming a domain-qualified scientific reviewer and a different schema
reviewer, neither an author; pilot-specific cases added to the suite.

**Phase 3 — regeneration. Mechanically complete, pending review.** The corrected foundations are
applied to all 650 profiles, not only the 630 outside the pilot, because the generator rebuilds the
whole tree from the declarations. No blanket item decision was carried over from the pre-review.
[`measurements/domain-diff-2026-09-15.md`](measurements/domain-diff-2026-09-15.md) records what
moved in each of the 26 domains, and `scripts/domain_diff.py` regenerates it against any baseline
commit. *Exit:* regenerated bundle with no fixture invariant violations — done; the scientific
suite's fixture invariants pass in both languages.

What that diff cannot tell anyone is whether a new value is *right*. It reports that a domain's
required-item count fell or that an operator appeared, not whether the profile now describes the
science correctly. That judgement is Phase 4's, and it is the reason this phase's completion is not
an approval.

**Phase 4 — domain review waves.** Review by domain, not by field. Each wave needs named reviewers
and produces evidence files. *Exit:* every profile has complete evidence, or is deprecated.

**Phase 5 — GA.** *Exit:* strict scientific suite green; every known defect closed or explicitly
accepted with a recorded reason; all sources pinned; `ga_ready` true; release notes state plainly
what approval does and does not mean.

**Versioning note.** Released objects are immutable, so corrections of this size land in a new
version. v0.1 is still `0.1.0-draft` / alpha, so pre-GA correction in place is possible; governance
should confirm which path applies before Phase 1 lands.

## 7. Independence

The scientific reviewer must be domain-qualified and must not have authored the profile. The schema
reviewer must be a different person, also not an author. Git history attributes all current profile
source to one author, so both reviewers come from outside that authorship. AI assistance may draft,
summarise and test; it is never the reviewer of record, and anything it drafts says so.

## 8. Risks

- **Regeneration churn.** Fixing the generator rewrites fixtures for hundreds of profiles. Mitigate
  with the fixture invariants in the suite and a per-domain diff review.
- **Snapshot maintenance.** Ontology, taxonomy and mapping snapshots must be pinned and refreshed
  deliberately; a stale snapshot silently changes answers.
- **Over-requirement.** Requiring too much turns real couplings into UNKNOWN.
  `scripts/compatibility_census.py` measures this: nine scenarios against all 650 profiles, tallied.
  The [baseline](measurements/README.md) is UNKNOWN 22.5%, INCOMPATIBLE 27.2%, EXACT 11.3%,
  DIRECT_COMPATIBLE 39.0% over 5,775 comparisons. Re-run it with `--baseline` after each fix. The
  census also quantifies D1 and D2: 526 of 650 profiles ignore a declared unit entirely, and the 124
  that do compare it refuse `g` against `kg`.
- **Unit migration.** Moving to UCUM spellings changes declared contracts and any lock that pins
  them; sequence it with the versioning decision above.
